## Isolation and limits

The candidate ran in disposable state on a separate loopback port. An SSH loopback forward exposed only that test port to the Linux client. Both production Gateways retained their original PIDs and remained healthy; no service restart or config change. The native test used a private HOME, Xvfb display, D-Bus session and credential vault. A read-only CLI shim supplied status and the real candidate-issued bootstrap URL, rejecting unexpected CLI actions. Actual auth, preferences, persistence, and subscriptions were not mocked. Test app, display, tunnel, Gateway and temporary state were cleaned up.

This is a **scoped native Linux smoke**, not a fresh exact-head native-shell build, not Wayland qualification, and not a Linux-hosted Gateway qualification. No worker inventory was seeded, so native rename/dismiss/expiry were not re-exercised. The earlier immutable paired-client/upgrade evidence remains the proof for those shared controller paths. Ctrl+R was sent but did not establish document reload; this report claims only the verified route leave/return, not native full reload/restart durability.

`native-driver.py` records the native harness (portable root path). It expects the extracted verified package at `app/usr/bin/openclaw-desktop`, a private genuine `private-login.json` generated by the isolated Gateway CLI, and an active loopback forward. That credential file is intentionally not published. Run under `xvfb-run -a -s '-screen 0 1440x1100x24' dbus-run-session -- python3 native-driver.py`. Route-return inputs were submitted through the driver's bounded `action.json` interface; the result JSON also incorporates the separate paired-client observer and visual inspection, not merely driver exit status.
